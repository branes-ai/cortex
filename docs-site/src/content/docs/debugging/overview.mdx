This section describes **how cortex debugs, tests and characterizes its VIO pipeline**: one
transformation at a time, each in its own test bench, each held to explicit invariants, in several
arithmetic types. It is the methodology of
[epic #444](https://github.com/branes-ai/cortex/issues/444). It builds on the
[stage contracts](/pipeline/overview/) of the VIO Pipeline section and the
[diagnostic methodology](/pipeline/diagnostic-methodology/) behind them.

## Why: the end-to-end number can't say *where*

The VIO filter still doesn't produce a trustworthy estimate, and the end-to-end metrics can't say
where it goes wrong:

- **The filter is over-confident.** NEES and NIS sit far above their χ² targets
  ([#212](/pipeline/consistency-analysis/)). The leading suspects are properties of the stages
  running *together*, so watching the final trajectory doesn't separate them.
- **A fix proven at one level underperforms at another.** The right-invariant EKF removes the yaw
  leak at the Jacobian level (0.39 → 2e-16), yet runs worse than the body-frame MSCKF end to end.
- **Several failures were numerical, not algorithmic:**
  - the square-root covariance diverged on real data (ATE 6e+40 m);
  - a barely-conditioned update produced a non-finite δx;
  - the invariant backend diverges under Clang but not GCC (#437: 58 m vs 3.4 m RMS).

  With only an end-to-end metric, an algorithmic fault and a precision or conditioning fault look
  the same.

ATE and RPE are measured *after* aligning away the very degrees of freedom VIO bugs live in, and a
EuRoC replay takes minutes to return roughly one bit of information. The
[diagnostic methodology](/pipeline/diagnostic-methodology/) page explains why steering by that
number fails. Epic #444 replaces it as the debugging instrument.

## What: an instrumented, divide-and-conquer environment

	</Card>

		check already exist. [#446](/debugging/capture-and-composition/)
	</Card>
	<Card title="The loop is checked as a loop" icon="random">
		*Planned.* Composition benches and trajectory-level checks will confirm that a fix fixes the

		[#447](/debugging/capture-and-composition/)
	</Card>
	<Card title="Mixed precision is a diagnostic" icon="seti:config">
		*Planned.* The pipeline's linear algebra moves onto MTL5, generic in the arithmetic type. A
		stage whose output moves between `double`, `posit<32,2>` and `float` is numerically fragile.
		The bench framework already runs a stage in several types, today for every bench except S4
		(the front end is not yet generic). The S6 benches
		found that a square-root filter must carry its factor: re-factoring the covariance in float or
		posit32 drops the clone directions.
		[#448–#451](/debugging/mixed-precision/)

## How: the method, step by step

1. **Cut the pipeline at its stage boundaries.** Each stage becomes a function whose only effect is
   on the state passed in, and which returns what happened instead of logging it. The backend
   becomes the readable call sequence S2 → S6 + S9 → S3 → S0 + S4 → S5 → S6a…S6e.
2. **Write down what each transformation must preserve.** The [invariant table](/debugging/invariants/)
   gives every stage its checks, from timestamp monotonicity at the inputs to "δx has no component
   along the unobservable directions" at S6e. A wrong output is caught at the transformation that
   produced it, not three stages later.
3. **Give each transformation a bench.** A [bench](/debugging/stage-benches/) runs that one stage on
   fixtures:
   - **known-answer:** synthetic input with an analytic expected output;
   - **ground-truth-injected:** truth fed in upstream;
   - **captured:** a stage boundary recorded from a real run.

   It runs each fixture in every arithmetic type and every implementation variant, and sweeps the
   conditions (noise, Δt, parallax, conditioning, window size) to CSV.
4. **Turn interesting moments of real runs into fixtures.** When a EuRoC run misbehaves, capture the
   stage boundary where an invariant first fails and debug it in that stage's bench, at the speed of
   a unit test.
5. **Confirm at the system level.** Some faults exist only in the loop. Composition benches and
   trajectory-level NEES/NIS confirm that a fix localized by a bench also fixes the filter.
6. **Use the arithmetic as an instrument.** Port the linear algebra to MTL5, stage by stage behind
   each bench, then run every stage in several number systems. Precision sensitivity becomes a
   per-stage measurement, not a guess.

<Aside type="tip" title="The method already found a bug">
  Proving that the stage refactor (#452) changed nothing, bit for bit on EuRoC, exposed a
  pre-existing heap-buffer-overflow in the square-root covariance update. That bug is the likely
  cause of the sqrt backend's real-data divergence. See the
  [worked example](/debugging/worked-example/).
</Aside>
