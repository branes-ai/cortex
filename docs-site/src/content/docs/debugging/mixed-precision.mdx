The same effort that makes every stage observable also puts the pipeline's linear algebra on
**MTL5**, generic in the arithmetic type. Running the pipeline in several number systems then
becomes a diagnostic of its own: **a stage whose output changes materially between `double`,
`posit<32,2>` and a wider type is numerically fragile.**

## Why it matters here

Several of the pipeline's failures were numerical:

- the square-root covariance diverging on real data;
- a non-finite δx from a barely-conditioned update;
- the Clang-only divergence of #437.

With per-stage arithmetic, "is this algorithmic or numerical?" becomes a measurement. Run the stage
in a wider and a narrower type on the same fixture, and see whether its invariants move.

## Today vs the port

Today the pipeline makes no `mtl::` calls. Its only MTL5 touchpoint is the `mtl::Scalar` concept
behind `math::Scalar`, and its linear algebra is hand-rolled:

| Today (hand-rolled) | MTL5 replacement |
|---|---|
| `msckf::DynMat<T>`, a row-major `std::vector` holding P, F, G, H, S, K | `mtl::mat::dense2D<T>` |
| GEMM/GEMV, transpose, add | `mat/operators.hpp`, `operation/mult.hpp`, `trans.hpp` |
| A·P·Aᵀ sandwiches (clone, predict, S, Joseph) | `mult` + `syrk`/`symm` |
| Cholesky, SPD solve | `operation/cholesky.hpp`, multi-RHS via `trsm.hpp`; `ldlt.hpp` for semidefinite S |
| Householder QR (R only), retriangularize | `qr.hpp`, `lq.hpp` |
| Triangular solves (square-root form) | `lower_trisolve.hpp`, `upper_trisolve.hpp`, `trsv.hpp` |
| MSCKF left null space | `householder.hpp` + `apply_householder_left` |
| Symmetric eigen, 3×3 SVD | `eigenvalue_symmetric.hpp`, `svd.hpp` |
| Principal-submatrix gather | `mat/view/map_view.hpp` |

## How the port is gated

1. **Safety gate first.** At `T = double`, the MTL5 port must reproduce today's results: the same
   EuRoC trajectories to ≤ 1e-9 relative, and all current tests, gates and inspector outputs
   unchanged. The bit-identical equivalence harness used for the
   [stage refactor](/debugging/stages-as-transformations/) is the model.
2. **Stage by stage, each behind its bench.** A stage is ported only when its bench passes on its
   fixtures in every type. A whole-pipeline check closes the port.
3. **Fix the sites that break or narrow a non-IEEE `T`:**
   - non-ADL math (`std::sqrt`, `std::acos` on `T`);
   - `static_cast<double>` on the estimation path;
   - fixed ridges and epsilons like `T(1e-9)` that vanish in 16-bit types, which should be
     T-relative;
   - the `double` timestamp mixed into `T`.

   By design, timestamps stay `double` and the telemetry accumulators in `eval/` stay `double`.
4. **Per-stage arithmetic.** Covariance and update math can run in one type while Jacobian assembly
   runs in another. A precision matrix of stages × types becomes the characterization report, and
   the diagnosis of #437.
5. **No latency regression.** `vio_bench` per-frame latency (p50, p99) on EuRoC V1_01 must stay at
   its pre-port level, or the change must explain the difference.

### The equivalence gate

Two tools hold a port to "same results". Run each before the port to take a reference, and after it
to compare:

```bash
# Stage benches: every built-in fixture, every variant, in double (117 outputs).
./build/tools/bench_snapshot --write before.json              # before the port
./build/tools/bench_snapshot --compare before.json            # after: 1e-12 normwise, per output

# EuRoC: every tracked pose and its σ, at full precision, per sequence.
./build/tools/vio_trajectory_report --dataset …/V1_01_easy/mav0 --label V1_01 --out ref/    # before
./build/tools/vio_trajectory_report --dataset …/V1_01_easy/mav0 --label V1_01 --out after/  # after
./build/tools/bench_snapshot --compare-trajectory ref/V1_01_trajectory.csv after/V1_01_trajectory.csv
                                                               # the gate: 1e-9 normwise, per column
cmp ref/V1_01_trajectory.csv after/V1_01_trajectory.csv       # optional: bit-identical too?
```

Both compares fail on anything they can't check:
- a fixture that throws;
- an output or column present on one side only;
- a non-finite value that isn't the same kind on both sides (NaN, or an infinity of the same
  sign).

### What the first family showed

The products port reproduces every bench output and all three EuRoC trajectories (V1_01, MH_05,
V2_03) **bit for bit**: MTL5 builds each entry in the same k order as the hand-rolled loop. It also
cost **+7 % p50 and +17 % p99** per-frame latency.

- **MTL5 5.12's generic dense product is an i-j-k dot product.** It walks B down a column and can't
  vectorize, so it ran 1.5–2.6× slower than the i-k-j loop it replaced at the filter's sizes
  (81×81, 81×15).
- **MTL5 has no CRS × dense-matrix product.** The hand-rolled loop skipped zero terms, which made
  F·P (F is the identity on the clone rows) and (I − KH)·P cheap.

Both were fixed upstream rather than worked around:
[mtl5#549](https://github.com/stillwater-sc/mtl5/issues/549) is a row-major i-k-j kernel,
bit-identical by construction, and [mtl5#550](https://github.com/stillwater-sc/mtl5/issues/550) is
`mult(compressed2D, dense2D, dense2D)`, both in
[mtl5#552](https://github.com/stillwater-sc/mtl5/pull/552). Against that branch the port is back to
baseline within about 0.5 % p50, with byte-identical trajectories. The remaining cost is building a
CRS copy per product, which a non-owning CRS view in MTL5 would remove.

### What the second family showed

The second family is the Cholesky factor and the SPD solves behind it. They serve the update's
S⁻¹ and Kalman gain, the χ² gate, initialization, triangulation and the NEES checks.

- **The solves port bit for bit.** `cholesky_solve` is now two `mtl::trsm` calls, forward through L
  and back through `trans(L)`. trsm's generic path subtracts each term in the same order as the
  hand-rolled substitution. All 117 bench outputs and all three EuRoC trajectories are identical,
  and latency is unchanged (V1_01 p50 30.86 → 30.85 ms, p99 37.51 → 37.49 ms, three interleaved
  runs each).
- **The factor does not.** MTL5's `cholesky_factor` forms each entry as a − (Σ products). The
  hand-rolled factor subtracts term by term. Both are backward stable, but they round differently:
  37 of 117 bench outputs move, and the filter loop moves by up to 2.5e-11.
- **On EuRoC, that rounding change is a different run.** On V2_03, 2 of 16,265 update accept/reject
  decisions flip, and the trajectory goes a different way from there (ATE 0.269 → 0.261 m, worst
  pose about 15 cm apart). The filter's discrete decisions amplify any rounding change. So the
  ≤ 1e-9 trajectory criterion only holds for a port that keeps the bits; a port that rounds
  differently needs a statistical comparison instead.
- **Neither ordering is more accurate.** In backward error ‖A − LLᵀ‖/‖A‖ at n = 81, term by term is
  about 2× better on ill-conditioned spectra like the filter covariance (cond 1e6–1e10), and the
  MTL5 order is about 1.4× better on well-conditioned ones.

So the factor stays in cortex. MTL5 is asked for an opt-in term-by-term ordering in
[mtl5#556](https://github.com/stillwater-sc/mtl5/issues/556), which would let it port bit for bit.
The same issue notes a smaller difference: `cholesky_factor` tests the pivot with `diag <= 0`, which
a NaN passes, while cortex's factor rejects it.

## The MTL5 gap register (#451)

Every operator the pipeline needs that MTL5 doesn't provide is recorded with its pipeline sites, the
interim workaround, and an upstream issue (stillwater-sc/mtl5). Known so far:

- scalar × matrix for non-arithmetic scalars (mtl5#538);
- a vectorizable generic dense product (mtl5#549) and a CRS × dense-matrix product (mtl5#550), both
  in mtl5#552;
- a non-owning CRS view over caller arrays (`compressed2D` copies them);
- block insert/scatter into `dense2D`;
- a symmetric A·P·Aᵀ primitive;
- a left-null-space helper;
- an opt-in term-by-term ordering in `cholesky_factor`, and NaN-pivot rejection (mtl5#556). Until
  then the factor is local. Multi-RHS solves need nothing new: two `trsm` calls do it;
- a matrix exponential.

Lie-group exp/log and Jacobians stay in `branes::math::lie`; they are not MTL5's job.
